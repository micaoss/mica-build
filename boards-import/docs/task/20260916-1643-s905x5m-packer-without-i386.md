# 20260916-1643-s905x5m-packer-without-i386 The s905x5m packer stage drops the i386 platform

- **status**: done
- **priority**: P3
- **owner**: tdpnmgkr
- **createdAt**: 2026-09-16 16:43

## Description

`boards/s905x5m/loader/package/Dockerfile` ran its packer stages
`FROM --platform=linux/386`, the only use of that platform in this repository
and the only reason `debian:trixie-slim` needs a `386` row at all. The stage
exists to run `aml_image_v2_packer`, the vendor tool pinned as the
`s905x5m-aml-image-v2-packer` source row of `locks/upstream.lock`.

## Findings

Measured against the published `uboot.s905x5m.20260916-0857` component, whose
`DDR.USB`, `u-boot.bin.signed` and `u-boot.bin.sd.bin.signed` were used as the
packer inputs together with this repository's `config/` and `blobs/` at 97aca03.

1. The pinned packer is an `ELF 32-bit LSB executable, Intel 80386, statically
   linked`. Being static it needs no 32-bit userland: an x86-64 kernel runs it
   through IA-32 emulation. It reports `version : 2.6.5` when run directly on
   an x86-64 host.
2. It is deterministic. Two packs of the same inputs, two seconds apart,
   produced byte-identical `update.img`.
3. Packing those inputs on an x86-64 host, outside any container, reproduced
   the published `update.img` byte for byte
   (`44a45fa2e0393354cf6826c5bff46271cbe8191fead5d2f26c4588ef574f34b3`), and so
   did packing them inside the pinned **amd64** `debian:trixie-slim`. The i386
   platform contributes nothing to the output.
4. Therefore `update.img` is not a second reproducibility defect: it follows
   `u-boot.bin.signed` exactly as
   [20260916-0620](20260916-0620-s905x5m-uboot-not-reproducible.md) assumed.
   That assumption is now measured.
5. There is no 64-bit vendor packer to pin instead. `khadas/utils` at the
   pinned commit `09fd7ae` carries `aml_image_v2_packer` three times --
   top-level (the row we pin), `aml-flash-tool/tools/linux-x86/` and
   `aml-flash-tool/tools/linux-arm/` -- and all three are 32-bit (i386, i386,
   ARM EABI5); the others are macOS and Windows builds.
6. An open implementation is not a byte-identical replacement. `hzyitc/AmlImg`
   (Go, `5ede4ed`) reads our container correctly -- it unpacked all 11 items of
   the published image -- but its `pack` writes 13671564 bytes where the vendor
   writes 10267648: it does not deduplicate the identical payloads the vendor
   shares between items (`DDR.USB`/`UBOOT.USB`, `_aml_dtb.PARTITION`/
   `meson1.dtb`) and writes 4 where the vendor writes 8 in the header field at
   offset 20. Both are version 2 containers (`0x27b51956` at offset 8).
   Switching to it would change every published `update.img`.
7. `aml-imgpack.py` (steeve, Khadas, LibreELEC) is not a candidate at all: it
   packs `AML_RES!` resource images, a different format. `AmlImg` keeps the two
   apart as `pack` and `res_pack`.

## Change

The packer stages are `FROM --platform=linux/amd64`: the packer is an x86
binary and the `uboot` component is x86-64 by contract (`tools/inputs.sh`
records `builder amd64` for it, and `build.yml` pins its job to an x86-64
runner). On an x86-64 builder the stage is now native rather than foreign; on
any other builder it is emulated exactly as the `386` stage was. The recovery
target of `boards/s905x5m/Makefile` moves with it.

## What this removes from the build matrix

- the only `linux/386` platform in this repository, so no builder needs to
  offer or emulate i386 any more;
- the `386` row of `debian:trixie-slim` in `locks/mica-build-env.lock` becomes
  unused by every consumer -- dropping it is `mica-build-env`'s change, and its
  `tests/publish-test.sh` asserts the row today. The three `debian:trixie-slim`
  rows all carry the same index digest, so no digest moves with it.

Nothing else changes: `tools/inputs.sh` reads `image_row debian:trixie-slim`
without a platform, so the `uboot` inputs hash moves only because the
Dockerfile bytes moved.

## Cost: one package version bump

`boards/s905x5m/Makefile` is listed in `PREPARE_INPUTS` of
`boards/s905x5m/extras/bluetooth/producer.env`, so editing the recovery
target's platform moved that producer's package inputs and the version guard
refused the arm64 pool of CI run 35124013662 ("The package versions against
each board's latest release"). Measured with `tools/deb/package-inputs.sh`
against a clean checkout of 97aca03: exactly one producer moved, `bluetooth`
(`94b89faac56d` -> `616a2d61c592`); the four board producers, both radio
producers and `wireless` were unchanged. `mica-s905x5m-bluetooth` is therefore
`0.1.0-5`.

This is the second time in two rounds that an edit to the board Makefile has
cost this package a bump, for a change that cannot reach its bytes.

**Decided 2026-09-16, and not to be re-opened as it stands: `PREPARE_INPUTS`
is NOT narrowed.** The cost measured here is one version bump on one package
when a board Makefile is edited. The risk on the other side is a package that
silently fails to rebuild because an input that *can* reach its bytes was not
declared -- staleness that a device finds, not CI. A version number is free;
that is not. The question comes back only with a measurement showing a larger
cost: several producers moved by one edit, or a bump on a package with a
downstream contract.
